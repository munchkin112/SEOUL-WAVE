# 한강버스 문화행사 추천 서비스 PRD v1.0

- DB 버전: **PostgreSQL 18** (사용자 확정). 세부 패치 버전·이미지 digest는 실제 배포에서 기록한다.
- 기준 버전: v1.0 / 개정일: 2026-11-05, Asia/Seoul
- 프로젝트: 교과목 3 멀티 에이전트 협업 및 서비스 운영
- 제출: 2026-11-09 15:00 / 발표: 같은 날 15:00 시작
- 상태: 제품 결정 D-01~13 승계. 9.3~9.8 운영 상세는 개정 권고안이며 구현·검증 완료를 뜻하지 않음.

## 1. 서비스 개요와 문서 안내

### 1.1 어떤 서비스인가

한강버스 이용자가 선택한 배편으로 하선한 뒤, **당일 방문 가능한 전시를 최대 3개까지 추천**받는 서비스다. 배편과 행사 운영시간, 하선 후 이동시간을 함께 검토해 실제 일정이 성립하는 후보만 보여준다.

### 1.2 사용자는 어떻게 이용하는가

1. 지원하는 출발→도착 구간과 오늘의 배편을 선택한다.
2. 필요하면 배 출발부터 사용할 총시간을 입력한다.
3. 서비스가 검수된 전시의 운영조건과 하선 후 이동 30분 이하 여부를 확인한다.
4. 조건을 통과한 전시와 추천 이유·시간 근거를 확인한다.
5. 맞는 전시가 없으면 같은 배편의 다른 행사를 먼저 검토하고, 필요한 경우 더 이른 배편을 별도 변경안으로 제시한다. 적격 후보가 없으면 없다고 안내한다.

### 1.3 이번 프로젝트의 구현 범위

| 구분 | 범위 |
|---|---|
| 지원 구간 | 검수 가능한 전시 2~3개를 확보할 수 있는 출발→도착 1개 구간 |
| 추천 대상 | 검수된 최대 3개 전시 중 당일·이동·일정 조건 통과 후보 |
| 입력 | 배편, 선택적 총시간. 취향·무료 필터 없음 |
| LLM 역할 | 이동·일정 검토, 근거 기반 추천 이유, Critic 검토 |
| 자동 복구 | 제한 재시도·검증·대체/중단 처리, DB 비정상 종료 시 Docker 재시작과 서비스 복구 확인 |
| 운영 화면 | 운영 조회는 필수. 네 영역 구성(전체·실행·장애·데이터)은 9.4의 권고안·팀 확인 전 |
| 완료 증거 | 실제 배포·연결·장애 시험·로그·알림을 동일 실행 및 제출 버전에 연결 |

조건부·필수 정보 미확인 후보는 공개하지 않는다. 당일 조회는 실시간 취소·매진 보장을 뜻하지 않는다. DB 수동 중지와 무응답은 비정상 프로세스 종료 자동 재시작과 구분한다.

### 1.4 문서를 읽는 순서

- **2~5장:** 해결할 문제, 범위, 사용자 시나리오, 기능 요구사항
- **6~7장:** 데이터와 멀티 에이전트 협업
- **8~9장:** 장애 복구, API·보안, 운영 대시보드와 로그
- **10~12장:** 배포·검증, 팀 책임, 제출 완료 기준
- **13장:** 현행 세부 계약과 승계 추적. 13.2~13.3은 현재 적용 계약이며 구현 시 반드시 확인
- **부록:** 결정 근거와 개정·검토 이력

공식 평가기준을 우선하며, 이 PRD는 제품 범위와 수용 기준을 정한다. 아키텍처 문서는 역할·API·DB·MVC·배포 구현을 구체화한다. **채택한 설계, 구현 완료, 시험으로 확인된 결과는 서로 구분한다.**

## 2. 제품 목적과 성공 조건

### 2.1 해결할 문제

한강버스를 타려는 사용자는 선택한 배편으로 도착한 뒤 당일 방문할 수 있는 전시를 따로 찾아야 한다. 운영시간·입장 마감·이동시간이 맞지 않거나 정보가 부족하면 실제 방문이 어려울 수 있다.

이 서비스는 **선택한 한강버스 배편을 기준으로 당일 운영하는 검수 전시를 최대 3개 목록 안에서 찾고, 하선 후 예상 이동시간 30분 이내 및 일정 조건을 통과한 행사만 추천 이유와 함께 제공한다.** LLM은 추천 이유와 검토를 맡고, 코드가 시간·허용 후보·제약을 검사한다. API·에이전트·DB·LLM 장애에는 제한 복구와 구분 가능한 기록을 적용한다.

### 2.2 사용자와 핵심 결과

- 일반 사용자: 회원가입 없이 지원 구간·오늘의 출발 회차·선택적 총시간을 입력하고 전시 후보를 비교한다. 취향·무료 여부를 입력받지 않는다.
- 운영자: 권한이 있는 화면/API에서 실행 단계, 수집 상태, 장애·복구·배포 결과와 증빙을 조회한다.
- 평가자: 동일 제출 버전의 정상 협업, Critic 검증, FT-01~04, 배포 차단·알림을 재현하거나 증빙으로 확인한다.

제품 성공은 화면에 추천 문장이 나오는 것만으로 판정하지 않는다. 실제 근거에 연결된 결과, 구분 가능한 에이전트 협업, 장애 대응 및 배포·시험 증빙을 함께 충족해야 한다. 만족도·복구율·응답속도의 실제 성과 수치는 측정 전 기재하지 않는다.

## 3. 과제 필수 요건과 제품 범위

### 3.1 2기 진행 가이드 적용

| 구분 | 이번 필수 완료 조건 | 선택 요건과 적용 방침 |

기존 평가 이미지의 배포·서비스 디스커버리·시크릿·관측·복구·파이프라인 평가 취지는 유지한다. 기술 적용 범위는 제공된 2기 가이드의 명시적인 필수/선택 표로 구체화한다. 가이드의 예시 수치·서비스 이름·컨테이너 개수·후반 포괄 체크리스트를 새로운 필수 기능으로 추가하지 않는다.

심사 배점은 기획·목표 달성 25, 서비스 완성도·활용 가능성 35, 수행 과정·개선 노력 20, 발표·전달력 20이다. 이번에는 기능 수 확대보다 정상 흐름 완성, 실제 장애 시험, 실패 후 개선 증거를 우선한다.

| 필수 | 이번 범위에서 제외 |

## 4. 사용자 흐름과 수용 기준

### 4.1 정상 화면 흐름

1. 클릭 노선도에서 검수된 출발→도착 구간 1개를 선택한다. 미지원 구간은 차단한다.
2. 조회일은 서버의 Asia/Seoul 오늘로 표시한다. 오늘 아직 출발하지 않은 회차를 선택하고 출처·계산 도착예정을 확인한다.
3. 선택적으로 배 출발부터의 총시간을 입력한다. 취향·무료 여부·자유문 선호 입력은 없다.
4. 서버는 최대 3개 검수 행사 목록에서 당일 운영, 검수 유효성, 하선 후 예상 이동시간 30분 이하, 운항·입장·관람 조건을 검사한다.
5. POSSIBLE 후보만 실제 확보 수대로 공개한다. 카드에는 추천 이유·일정·이동수단/예상시간·위치·운영조건·알려진 요금·출처·수집/검수 시각을 표시한다. 요금은 선택 필터가 아니다.
6. 일정 충돌 시 같은 배편의 다른 검수 행사를 먼저 찾고, 없으면 오늘의 아직 출발하지 않은 이전 회차를 별도 변경안으로 제시한다. 변경안도 모든 조건을 통과해야 한다.
7. 적격 후보가 없으면 ‘오늘 조건에 맞는 검수 전시가 없습니다’와 일반적인 제외 사유를 표시한다. 조건부 카드·미검수 행사·과거 행사로 채우지 않는다. API/DB 장애로 조회할 수 없는 경우는 이용 불가로 구분한다.

총시간 안내: “배 출발부터 관람 종료까지 배 이동·하선 후 이동·대기·관람을 포함하며 귀가는 제외합니다. 하선 후 행사장까지의 예상 이동은 30분 이내인 경우만 안내합니다.”

| ID | 현재 요구사항 | 수용 기준 / 이전 버전 처리 |
|---|---|---|
| FR-01 | 지원 구간 1개 선택 | 검수된 출발·도착·운항 방향만 허용. 실제 조합은 데이터 확인 후 확정. |
| FR-02 | 시간표·계산 도착예정 | 원문 출발 시각+구간 소요시간 합계를 사용하고 계산값·출처·버전을 표시. |

## 6. 데이터와 일정 판단 원칙

### 6.1 시간표 데이터

기존 시간표 JSON과 원본 자료를 재사용한다. 이전 문서의 준비 기록은 8개 선착장 ID, 34개 계산 조합, 예상값 300건, 원문 시각 140개·빈칸 52개다. 이는 당시 데이터 준비·계산 기록이며 현재 운항 여부나 제품 지원 범위의 증거가 아니다. 기존에 언급된 7개 선착장 목록과 데이터의 8개 ID 차이도 실제 구간 선정 때 확인한다.

- 도착예정은 선택한 출발 시각에 구간별 소요시간을 합산한다. 중간 선착장의 출발시각·빈칸으로 같은 항차를 추론하지 않는다.
- 원문 출발 시각이 없으면 선택 항목을 만들지 않는다. 환승·미지원 직항 조합은 허용하지 않는다.
- 공식 도착 열은 별도로 보존한다. 계산값을 공식 도착 시각·실시간 도착으로 표현하지 않는다.
- 회차 키는 로컬 데이터 참조이며 공식 항차 번호가 아니다.
- 실제 서비스 날짜의 운항 여부·예외·시간표 적용 기간을 검수한다. 확인되지 않으면 전체 여정의 불확실성에 반영한다.
- 날짜와 시각은 Asia/Seoul을 기준으로 함께 처리하고 자정 경계를 보존한다. 오늘 이미 출발한 배편은 대안으로 제시하지 않는다.

### 6.2 문화행사 원천과 수집

서울열린데이터광장 「서울시 문화행사 정보」를 기본 원천으로 사용한다. 공식 설명은 행사명·분류·기간·장소·위치·요금·행사시간 등의 제공과 매일 1회 갱신을 안내한다. 모든 행사에 모든 값이 채워져 있거나 예약 상태·입장 마감까지 제공된다는 뜻은 아니다.

기존 PRD의 보존 대상은 `TITLE`, `CODENAME`, `STRTDATE`, `END_DATE`, `DATE`, `PRO_TIME`, `PLACE`, `LAT`, `LOT`, `IS_FREE`, `USE_FEE`, `PROGRAM`, `ETC_DESC`, `ORG_LINK`, `HMPG_ADDR`, `MAIN_IMG`다. 실제 서비스명·인증 호출·필드 존재·좌표 정의는 샘플로 검증해야 한다. 필드 이름만으로 위경도 매핑을 확정하지 않는다.

수집은 사용자 요청과 분리해 **매일 09:00(Asia/Seoul)** 한 번 수행한다. 원천 API의 제공자 측 실제 갱신 완료 시각은 아직 미확인이다. 모든 페이지와 건수·필수 구조를 확인한 후 성공 스냅샷을 확정한다. 실패한 일부 페이지만으로 기존 성공본을 덮어쓰지 않는다. 원문·수집시각·스키마 버전·정규화 버전·오류를 보관하고, 요청 실행은 사용한 스냅샷을 고정한다.

정상 수집 0건, 필터 결과 0건, API 실패, 성공 수집본 없음은 별도 상태다. 안정적인 공식 ID가 없다면 행사명만으로 동일성을 판단하지 않고 검증 가능한 식별·중복 조정 규칙을 하위 데이터 명세에 정의한다.

### 6.3 소수 후보 직접 검수

지원 구간은 당일 조회에 사용할 전시 2~3개의 운영·이동 근거를 검수할 수 있는 곳으로 조사 후 확정한다. 운영 검수 목록은 최대 3개이며 당일마다 유효성을 확인한다. 시연은 실행 당일 조회에 집중하고 날짜를 과거로 돌려 후보를 확보하지 않는다. 문서의 마곡→여의도 예시는 구간 결정이 아니다. **회의 조사 후보인 ‘야외 조각전’은 아직 운영 검수 목록의 유효한 추천 건으로 확정되지 않았다.** 행사 API 등록, 오늘의 전시 유지 여부, 실제 입구와 이동수단/분·운영시간·입장 조건·출처/확인일을 확인해야 한다. 11월 14일을 발표일인 11월 9일의 당일 조회 결과처럼 사용하지 않는다.

검수 기록에는 다음을 포함한다.

| 대상 | 반드시 남길 근거 |
|---|---|
| 선착장·행사장 | 좌표·입구 위치·권역·출처·검수일 |
| 행사 조건 | 행사 ID/버전, 적용 날짜·회차, 운영시간·휴관·입장 마감·요금·예약 조건의 출처와 발췌 |
| 이동 | 선착장 하선 지점/출구→행사장 입구, 이동 방식·경로, 예상 소요시간, 자료/지도 링크·확인일·적용 범위 |
| 관람 | 정해진 공연 길이 또는 검수한 전시 관람시간과 그 근거. 별도 희망 체류시간 입력은 현재 범위에 없음 |
| 검수 상태 | 검수자·검수시각·유효기간 또는 재검수 조건·누락/충돌 사항 |

이동시간은 확인한 자료에 기반한 **예상값**이다. 개인별 보행 속도·현장 대기·접근성을 보장하지 않는다. 직선거리를 속도로 나누어 검수된 실제 도보시간처럼 사용하지 않는다. 근거 없는 하선·이동 여유시간을 몰래 더하거나 0으로 처리하지 않고, 계산 가정은 공개한다.

원천이 바뀌었거나 적용일이 맞지 않으면 기존 검수값을 자동 승계하지 않는다. 예약 필요 정보만 있고 사용자의 예약 확보 여부가 없으면 예약 완료로 판단하지 않는다. 출처 간 충돌은 운영자가 해결하기 전까지 UNKNOWN으로 다룬다.

### 6.4 당일·이동 30분·검수 필터

서버의 Asia/Seoul 날짜를 service_date로 사용하고 오늘 운영하는 검수 전시만 대상으로 한다. 행사 전체 기간에 포함돼도 휴관·운영시간·입장 마감을 별도로 검사한다. 날짜가 바뀌거나 선택 배편이 출발했으면 결과를 재검증한다.

하선 지점부터 행사장 입구까지 검수된 예상 이동시간이 30분 이하인 후보만 허용한다. 이동수단은 이번 결정에서 특정하지 않았으므로 검수 기록에 실제 수단·경로·포함 구간을 명시한다. 대기·환승이 있는 이동은 필요한 시간을 포함해 검수해야 하며 누락되면 제외한다. 직선거리에서 시간을 추측하지 않는다. 하선 소요시간이 이동값에 포함됐는지 구분해 중복 합산하지 않는다.

취향·분위기·유무료 선호·자유문 조건 입력을 제거한다. 요금은 원천 정보로 보존하지만 필터·개인화 점수에 사용하지 않는다. 단순 요금 누락은 ‘요금 미확인’으로 안내하며, 운영·이동·예약 등 방문 판단 필수 정보 누락과 구분한다. 무료라고 추정하지 않는다.

표시 순서는 코드의 일정 적합성 검사 후 예상 이동시간 오름차순, 동률이면 안정적인 행사 ID 순서를 초기안으로 한다. 개인 취향 적합도 순위로 표현하지 않는다. 총시간 예산은 선택형/숫자 입력이며 입력하지 않으면 90분을 임의 생성하지 않는다.

### 6.5 일정 계산

공통 기준:

```text
예산 종료 = 선택한 배 출발일시 + 사용자 총시간 예산
행사 도착예정 = 계산된 배 도착예정 + 확인한 하선·이동 소요시간
최종 종료 한도 = 총시간 입력 시 예산 종료; 미입력 시 사용자 예산 한도 없음
```

총시간이 입력되지 않았다면 임의의 90분을 사용자 제약으로 생성하지 않는다. 운영조건 자체는 계속 확인한다. 배편 변경안은 총시간을 입력한 경우 같은 길이를 새 출발시각에 적용한다. 별도 종료일시·희망 체류시간은 현재 입력 범위에 없다. 총시간 미입력 시 예산 종료 비교를 생략하고 검수 관람시간과 폐장·입장 마감은 계속 검사한다.

| 행사 유형 | 판단 규칙 |
|---|---|
| 자유 입장 전시·체험 | 방문 시작=max(행사 도착예정, 개장). 입장 마감 이전인지 확인하고, 검수된 필요 관람시간을 더한 종료가 폐장·최종 종료 한도 이내인지 비교. |
| 고정 시각 공연·예약 회차 | 도착이 해당 회차의 공식 입장 조건·시작시각에 맞는지 확인. 공연 종료/길이와 총시간을 비교. 늦게 도착한 시각부터 관람을 시작하는 산식으로 바꾸지 않음. |
| 유형·필수 조건 미상 | 확인 가능한 충돌만 판정. 부족한 조건을 명시하고 방문 가능을 확정하지 않음. |

`END_DATE`는 행사 전체 종료일이며 매일 폐장시각이 아니다. 폐장과 입장 마감도 다르다. 조건이 적용되지 않음은 확인 근거가 있을 때만 사용하며 빈 필드를 적용 없음으로 간주하지 않는다.

### 6.6 방문 가능성과 최신성

| 상태 | 기준 |
|---|---|
| POSSIBLE | 방문일 운항·이동·행사 유형별 필수 조건이 확인되고 수치 비교와 하드 제약을 통과. “확인한 자료와 예상시간 기준 가능”으로 표시. |
| CONDITIONAL | 필수 이동·운항·운영·예약 조건 등이 미확인인 내부 판정. 추천 카드와 변경안에서는 제외하고 누락 사유를 trace에 기록. |
| IMPOSSIBLE | 확인한 날짜·시간·하드 제약과 충돌. 요금은 표시 정보로만 사용. 충돌 이유와 근거를 보존하고 일반 추천 후보에서는 제외. |

확인된 불가 조건은 다른 필드가 누락됐다는 이유로 조건부로 바꾸지 않는다. 운항일 UNKNOWN을 행사 카드 바깥에만 숨긴 채 전체 여정을 POSSIBLE로 표시하지 않는다.

최신성은 별도 `FRESH / STALE / UNAVAILABLE`로 관리한다. 세부 분류 권고안: 24시간 이내의 성공본이며 최신 예정 수집이 성공한 상태는 FRESH, 최신 수집이 실패해 허용 성공본으로 대체하는 상태는 STALE, 성공본 없음 또는 나이 24시간 초과는 UNAVAILABLE이다. 정확히 24시간은 허용한다. 요청 접수와 최종 공개 시점 모두 고정 성공본의 나이를 검사한다. 실행 중 24시간을 초과하면 DATA_UNAVAILABLE로 종료하며, 다른 스냅샷으로 조용히 교체하지 않는다. 저장 결과를 나중에 다시 조회할 때도 만료 결과를 현재 유효한 추천으로 표시하지 않는다. 최초 예정 수집 전 성공본은 유효기간 안이면 FRESH로 보며 마지막 수집 상태를 별도로 표시한다. 일일 수집 실패 시 DB가 정상이고 **마지막 성공 배치 완료로부터 24시간 이내**인 성공본만 사용한다. 보관은 최근 성공 스냅샷 2개까지 하되, 오래된 보관본이 존재한다는 이유로 24시간 제한을 늘리지 않는다. 매일 09:00 수집이 실패하면 직전 일자의 성공본이 24시간 이상 지나 곧 `UNAVAILABLE`이 될 수 있다. 최신성 한도를 넘었거나 성공본이 없으면 추천을 중단한다. 갱신주기가 하루 1회여도 당일 변경의 반영을 보장하지 않는다.

## 7. 멀티 에이전트와 LLM에 대한 제품 요구

### 7.1 필요한 협업

최소 3개의 구분되는 에이전트와 Critic 책임을 실제 실행으로 보여준다. 업무는 ① 선택 배편·이동계획의 근거 검토 및 대안 판단, ② 검수 행사 정보에 근거한 추천 이유 작성, ③ 일정·추천 결과의 의미 검토와 수정 요청이다. 취향 해석 제거 후에도 역할별 입력·허용 도구·판단·Handoff를 구분하며 단순 조회 함수를 에이전트 수로 세지 않는다.

일정 검토 역할에 Critic 책임을 결합하는 구조도 검토할 수 있다. 별도 검증기를 두더라도 코드 검사 모듈을 자동으로 LLM 에이전트 1개로 계산하지 않는다. 공식 가이드의 “3개 이상, Critic 포함”을 “도메인 3개+별도 Critic 반드시 추가”로 확대하지 않는다.

협업 구조는 응답속도·결정 일관성·장애 격리에 대한 선택 근거를 제시해야 한다. 최종 상태·재탐색·복구 적용·종료의 소유자는 하나로 정한다. 각 에이전트가 다른 에이전트를 무제한 재귀 호출하지 않는다.

### 7.2 LLM과 코드의 역할

| LLM에 맡길 판단·해석 | 코드가 보장할 처리 |
|---|---|
| 선택 배편·이동 근거 검토와 대안 설명 | 구조화 입력·타입·허용 ID·권한 검사 |
| 원문에 있는 운영조건의 보조 추출 | 날짜·시간·거리 계산 및 결정적 충돌 판정 |
| 허용 후보의 일정·이동 근거 기반 추천 이유 | 스냅샷·후보 ID·출처·정규화 값 일치, 이동 30분·당일 조건 검사 |
| 검증 결과의 설명·허용 대안 요청 | 재시도·호출·시간·비용 한도, 상태 전이, 최종 저장 |
| 추천의 의미적 일관성 검토 | 미검증 출력 차단, 허용 도구만 실행 |

코드는 임의 자연어의 모든 의미를 자동으로 증명할 수 없다. 필터 조건·가격·시각·행사 유형처럼 검증 가능한 주장과 이를 연결한 짧은 이유를 기본으로 하며, 근거 없는 분위기·품질·접근성 주장은 확정 문장에서 제거하거나 미확인으로 표시한다. Critic 검토를 거쳐도 사실성 100%를 주장하지 않는다.

LLM은 전체 원천을 무제한 읽지 않고 필터링된 후보를 사용한다. DB·도구 결과 안의 지시문은 데이터로 취급한다. 새 행사·좌표·시간·요금·URL을 만들거나 사용자 하드 제약을 바꾸지 않는다. LLM 장애 시 비구조화 문장을 그대로 공개하지 않는다.

### 7.3 Handoff·메모리·최종 검증 요구

다음 실행에 목적·입력 참조·사용자 제약·기대 출력·완료 단계·중간 결과·근거·실패 원인·시도 횟수·남은 예산을 누락 없이 전달한다. 실행/작업/전달 식별자와 송수신 주체, 스키마·데이터·모델·프롬프트 버전을 추적한다. 원문은 필요한 부분 또는 접근 가능한 참조로 전달한다.

기존 초안의 16개 필드 목록은 하위 계약 설계의 출발점이며 고정된 필드 개수 자체가 제품 요건은 아니다. 초기 단계에서 아직 없는 이동 계획·후보를 가짜 값으로 채우지 않도록 공통 필드와 단계별 필수값을 구분한다. `run_id`만으로 다수 작업·반복을 구분할 수 없다면 `task_id`·`step_id`를 추가한다.

Critic은 통과·수정 요청·중단 권고와 사유를 반환하고, 단일 조정 주체가 예산·제약을 적용해 다음 단계와 종료를 결정한다. 후보 조회 성공·JSON 형식 통과만으로 최종 성공을 선언하지 않는다. 최종 공개 결과와 필수 실행 기록의 저장이 완료되어야 성공을 반환한다.

### 7.4 협업 구현 기준과 런타임 제안

- **회의 채택 구현 방향:** Python과 LangGraph StateGraph로 이동 검토·문화행사 설명·일정 검토/Critic의 세 역할을 연결한다. 기존 코드와 의존성을 확인하고 설치·연결·실행 검증 결과를 기록한다. Python 세부 버전 제안과 LangGraph 채택 상태는 구분한다. 단순 노드 세 개 생성으로 에이전트 요건 충족을 주장하지 않는다.
- **설계 원칙:** Supervisor가 공유 상태·예산·전이·종료를 단일 소유한다. 에이전트는 다음 행동을 제안하며 코드가 허용 여부를 결정한다. 그래프 재귀 제한만으로 업무 예산을 대체하지 않는다.
- **설계 원칙:** LLM 공급자 호출을 교체 가능한 어댑터로 분리한다. 기존 OpenAI API 방향은 승계하며 특정 모델은 계정 사용 가능 여부·실호출·비용·지연 검증 후 정한다. 키와 비밀값은 프롬프트·공개 응답·로그에 포함하지 않는다.
- **현재 역할 적용:** 이동 에이전트는 계산된 이동계획·운항 근거의 검토와 허용 대안 판단, 행사 에이전트는 검수 후보의 추천 이유 작성, 일정/Critic은 일정·근거·설명 일관성 검토를 맡는다. 취향 해석·무료 필터·개인화 순위는 만들지 않는다.
- **검증 경계:** 코드가 당일·이동 30분·허용 목록 최대 3개·ID·스키마·산술을 검사한다. Critic은 의미 일관성을 검토한다. 코드 Validator·Recovery는 에이전트 수에 산입하지 않는다.
- **실행 기록:** 역할별 입력·도구·출력·Handoff·모델/프롬프트 버전·수정/거부 사유를 남긴다. 그래프 상태와 PostgreSQL에 저장된 실행 결과를 연결한다. 별도 체크포인트 저장소·추가 브로커 도입은 필수가 아니다.
- **연결 검증:** 제출 전 실제 LLM을 연결한 전체 정상 흐름을 최소 1회 확인한다. 이는 반복 mock 장애 시험을 대신하지 않는다. CI에서는 고정 응답과 mock을 사용하고 실제 연결 증거는 별도로 보관한다.

## 8. 결과·장애·복구 정책

### 8.1 상태 구분

하위 계약은 적어도 다음 네 축을 구분해야 한다. enum 명칭은 계약에서 확정하되 서로 다른 의미를 한 값으로 합치지 않는다.

| 축 | 의미와 예시 |
|---|---|
| 실행 상태 | 대기·실행 중·성공·기능 축소·실패·안전 중단 |
| 추천 결과 | 적격 후보 있음, 적격 후보 없음, 데이터 이용 불가. 조건부는 공개 결과 종류로 사용하지 않음. |
| 후보 방문 가능성 | POSSIBLE, CONDITIONAL, IMPOSSIBLE |
| 데이터 최신성 | FRESH, STALE, UNAVAILABLE |

정상적으로 모든 조건을 확인했으나 행사가 0건인 것은 성공적으로 수행한 조회의 빈 결과다. 필수 정보 누락으로 내부 제외된 후보도 시스템 장애와 구분한다. 재탐색 횟수를 채운 뒤 적합 후보가 없는 경우는 후보 없음으로 정상 종료할 수 있다. 실행 deadline 초과·필수 데이터 미확보·필수 저장 실패·검증을 통과하지 못한 출력은 실패/중단 또는 명시적 기능 축소로 기록한다.

### 8.2 업무 대안 탐색

1. 원래 배편·오늘·도착지·이동 30분·총시간 제약을 유지하며 최대 3개 검수 목록 안에서 다른 전시를 찾는다.
2. 없으면 같은 지원 구간의 오늘 아직 출발하지 않은 이전 배편을 **제안**하고 이동 30분·전체 일정·총시간을 다시 검증한다.
3. 필수 조건이 미확인인 후보는 내부 제외하고 사용자 추천·변경안으로 제시하지 않는다.
4. 후보가 없으면 없음과 이유를 반환한다. 사용자가 선택을 바꾸기 전에는 원래 배편을 유지한다.

업무 대안 탐색과 일시 오류 재시도는 서로 다른 작업·카운터다. 이미 검사한 배편·행사·버전 조합을 이유 없이 반복하지 않는다. 오늘·총시간·이동 30분 제약과 도착 선착장을 자동 변경하지 않는다.

### 8.3 장애 대응

| 상황 | 기대 동작 | 복구 기록 |
|---|---|---|
| LLM/API 일시 timeout | 제한 재시도 후 가능한 경우 같은 검증 후보의 기본 정보 제공 | 설명·검토 대체와 원 의존성 복구를 구분 |
| LLM 형식 오류 | 스키마 차단→수정 요청 한도 적용→검증된 기본 정보 또는 중단 | 잘못된 출력 미노출, 실제 호출·수정 횟수 |
| 에이전트 예외 | 안전한 단계만 한도 내 재실행, 지속 실패 종료·알림 | once/persistent 구분, 중복 저장 없음 |
| 문화행사 수집 API 실패 | 부분 배치 공개 금지, DB의 허용된 최신 성공본 사용 | 실패 배치·사용 스냅샷·나이·대체 이유 |
| 행사 성공본 없음/만료 | 데이터 이용 불가, 수집 상태 안내 | 후보 없음과 구분 |
| 필수 데이터 UNKNOWN | 해당 후보 추천 제외. 적격 후보가 없으면 정상 빈 결과 | 누락 원인과 근거를 내부 trace에 기록 |
| Critic 거부 | 사유가 있는 수정만 허용, 예산 소진 시 안전 중단 | 거부 근거·수정 지시·최종 미노출 |
| DB 연결/필수 저장 실패 | D-13: DB 비정상 종료에 Docker 자동 기동 적용, API는 제한 재접속; 복구 전에는 이용 불가·Discord·독립 로그 | Docker 재시작 여부와 실제 조회·필수 저장·API 정상 회복, 수동 개입 여부를 구분 |

LLM 설명·검토가 실패하면 코드로 당일·이동 30분·필수 일정 조건을 검증한 동일 후보의 기본 정보만 기능 축소 상태로 제공한다. Critic의 명시적 거부나 필수 조건 미확인은 대체 경로로 우회하지 않는다.

DB가 정상일 때 저장된 행사 성공본을 사용하는 정책은 **문화행사 API 장애 대응**이다. DB 장애 시 로컬 캐시로 추천을 계속하는 정책이 아니다. DB 이용 불가 중에는 시간표가 읽히더라도 전체 서비스 성공으로 응답하지 않는다.

DB 외부 로그에는 요청/실행/장애 ID·단계·시각·재접속 시도·Docker 재시작 여부·알림 결과를 남긴다. Discord 실패도 기록한다. **DB 컨테이너 비정상 종료 자동 재시작은 D-13으로 채택**했다. Docker 자체의 재시작이 완료되어도 DB 준비 및 앱 재연결·조회·저장·응답이 회복되지 않으면 자동 복구 성공이 아니다. 운영자가 DB를 수동 재가동했다면 수동 복구로 집계한다. `docker compose stop db`는 의도적 중지로 `unless-stopped` 자동 복구 대상이 아니며, DB가 살아있지만 응답 없는 경우도 `healthcheck`만으로 재시작되지 않는다. FT-03 시험 주입 방식에 따라 자동 복구 또는 기존 A안의 안전한 중단·알림·수동 복원을 각각 검증하고 강사 기대 동작은 별도 확인한다.

### 8.3.1 PostgreSQL Docker 설정·복구 확인 예시 (채택 방향, 코드 적용 전)

```yaml
services:
  db:
    image: postgres:18  # 사용자 확정 메이저 버전; 배포 시 패치 버전 또는 digest 기록
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - postgres_data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

공식 postgres:18 이미지의 기본 PGDATA는 `/var/lib/postgresql/18/docker`이며, 영속 Volume은 `/var/lib/postgresql`에 마운트한다. 기존 다른 메이저 버전의 데이터가 있으면 이미지 태그만 교체하지 않고 별도 데이터 이전 절차를 확인한다. 근거: [Docker 공식 PostgreSQL 이미지 문서](https://github.com/docker-library/docs/blob/master/postgres/content.md#pgdata).

위 예시는 **별도 DB 컨테이너와 영속 저장소, 자동 재시작, 상태 확인**을 표현한다. 실제 프로젝트의 기존 Compose를 지우거나 덮어쓰라는 지시가 아니다. `healthcheck`는 준비 상태 표시일 뿐 자체 자동 재가동 기능이 아니다. 운영 환경에 맞는 비밀값 관리, `api`·`worker`의 DB 재연결, 실제 복구 검증은 별도 구현해야 한다. `docker compose stop db`를 자동으로 되돌리려면 현재 채택 범위를 넘어서는 **독립 감시 주체**가 필요하며, Docker 제어 권한의 보안 위험까지 평가해야 한다.

### 8.4 운영 수치의 초기안과 확정 방법

다음 표의 `채택` 값은 이번 회의에서 선택된 **구현 운영 설정**이며 공식 과제 수치·이미 시험된 성능 수치는 아니다. `기존 유지`와 `미정`도 구분한다. 아키텍처/환경 설정에 단일 값으로 반영하고 실제 시험에서 한계를 검증한다.

| 항목 | 적용 값 | 상태·조건 |
|---|---|---|
| 전체 요청 실행 한도 | **90초** | 채택. 사용자 응답속도 성과 수치가 아님. 제한 초과 시 안전 중단. |
| LLM 1회 timeout | **15초** | 채택. 남은 전체 시간보다 길게 대기하지 않음. |
| 전체 LLM 호출 상한 | **8회** | 채택. 모든 역할·대안 탐색·형식 수정·SDK 자체 재시도까지 합산. SDK 숨은 재시도 설정도 통제. |
| 업무 재탐색 상한 | 2라운드 | 기존 제안 유지(확정 전). 기본 탐색 이후 추가 탐색. 중첩 루프 금지. |
| 외부 API/LLM 일시 오류 추가 재시도 | **최대 2회** (최초 포함 최대 3번) | 채택. timeout/일시적 서버 오류 등에만 적용, 영구 오류 제외. 호출 사이 짧은 지연 및 전체 시간/호출 상한 적용. |
| LLM 출력 형식 수정 | **최대 1회** | 채택. 위 재시도와 별도 사유로 기록하되 전체 LLM 8회에 포함. |
| DB 연결 재시도 횟수·기간 | 미정 | FT-03 기존 제한 재접속 유지. 외부 API 재시도 2회를 DB에 무단 적용하지 않음. 복구 중 DB 재연결/쓰기 중복 방지·총 90초 예산 반영. |
| PostgreSQL 컨테이너 종료 시 Docker 정책 | **`restart: unless-stopped`** | **채택 D-13**. 예상치 못한 프로세스 종료 자동 재기동. 수동 `stop db`/healthcheck 실패 자체는 자동 재시작하지 않음. 재시작 시도 횟수는 별도 고정 상한 없음. |
| DB 준비·복구 확인 | **DB 준비 + 조회 + 필수 저장 + API 정상 응답** | **복구 완료 조건 채택**. Health Check만 통과해도 서비스 복구 성공 아님. 알림 임계 횟수·재연결 대기 간격은 미정. |
| 결과 카드 수 | 최대 3개 | D-07 기존 제품 결정 유지. 확보 결과 0~2개도 허용. |
| 문화행사 수집 시각 | **매일 09:00 KST** | 채택. 단일 스케줄 실행 주체·중복 실행 방지, API 공개 시각 확인 필요. |
| 성공본 최대 나이 | **24시간** | 채택. 직전 성공 배치 완료시각 기준. 경계 초과 시 `UNAVAILABLE`. |
| 로그·실행 기록 | **7일** | 채택. DB 자체가 멈춰도 로그가 사라지지 않도록 독립 보관. |
| 성공 스냅샷 보관 수 | **최근 2개** | 채택. 성공 완료된 전체 배치만 보관 대상으로 계산. 오래된 것은 추천에 사용하지 않음. |
| CI 코드 커버리지 목표 | **70% 이상** | 채택. 핵심 테스트 전체 통과를 함께 요구하고 실제 측정 범위는 명세에 표시. |

수집 API timeout, 최초 수집 실행 시각의 정확한 처리, 모델명·금액 상한, 세션/보관 정책의 세부 저장 위치, FT-03 DB 재접속 횟수·간격과 재시작 실패 경고 임계값은 담당자가 첫 통합 시험 전에 정한다. Docker 비정상 종료 자동 재시작 정책 자체는 D-13으로 확정되었다. 무제한을 기본값으로 두지 않으며 확정하지 않은 항목을 완료라고 기록하지 않는다. 특히 **09:00 수집 + 성공본 24시간** 조합에서 다음 날 09:00 수집이 실패하면 직전 성공본이 만료될 수 있다. 이는 사용자에게 `DATA_UNAVAILABLE`로 알리는 현행 PRD 정책을 따른다.

## 9. API·보안·운영 제약

### 9.1 API의 업무 경계

아래는 기능 진입점 기준안이다. 정확한 JSON Schema·HTTP 오류·비동기 구현 방식은 하위 API 명세로 확정한다.

| 진입점 | 책임 |
|---|---|
| `GET /api/stops` | 선착장과 실제 지원 조합·표시 상태 |
| `GET /api/trips` | 날짜·지원 구간의 로컬 출발 항목, 계산 예상값·운항 확인 상태 |
| `GET /api/events` | 코드 필터 후보·원문·신선도. 사용자 여정의 최종 승인과 구분 |
| `POST /api/itineraries` | 오늘의 배편·선택적 총시간 기반 실행 접수와 run_id. 취향·무료 필터 없음. |
| `GET /api/runs/{run_id}` | 본인 실행의 진행·대안·검증 결과 조회 |
| 운영 조회·health | 권한 있는 실행/장애/수집 조회, 프로세스 생존과 DB·데이터 준비 구분 |

이번 회의에서는 FastAPI가 PostgreSQL에 실행 작업을 기록하고 별도 worker가 처리하는 방식을 채택한다. 요청 접수 시 비동기 `202`를 사용한다면 **요청·잡의 필수 저장에 성공한 후에만** 접수 완료로 응답한다. 중복 요청·재시작에 따른 중복 실행과 중복 완료를 방지한다. 이전 초안의 `POST /api/runs`를 별도 파이프라인으로 이중 구현하지 않는다. 실제 사용 클라이언트가 있을 때만 호환 필요성을 검토한다.

공개 결과에는 사용한 이동 정보, 행사 ID·버전·제목·분류·장소·거리 유형·기간/시간·요금·공식 링크, 추천 이유·근거·불확실성, 방문 가능성, 데이터 수집·검수 시각이 연결되어야 한다. 원문 전체·내부 연결정보·비밀값은 노출하지 않는다.

### 9.2 보안과 관측

- 비회원이라도 실행 결과의 세션 소유권을 검사한다. run_id를 안다는 이유만으로 조회를 허용하지 않는다.
- 운영 조회·장애 주입·수동 수집은 별도 권한 경로로 제공한다. 일반 서비스의 장애 주입 기능은 비활성화한다.
- DB 쿼리는 파라미터 바인딩을 사용한다. LLM에 임의 SQL·셸·배포·내부 URL·DB 관리 도구를 주지 않는다.
- 원문과 LLM 출력의 HTML을 그대로 실행하지 않는다. 외부 링크는 원천에서 검증한 공개 링크를 사용한다.
- DB·LLM·문화행사 API·Discord·AWS·SSH 비밀값은 서버/CI secret으로 관리한다. API 키가 경로에 있는 인증 URL도 로그에 남기지 않는다.
- 입력 길이·요청 빈도·동시 실행·호출/시간/비용 한도를 둔다. 무한 재시도·무한 알림을 막는다.
- 구조화 로그에 run/step/handoff ID, 오류 유형, 시도·대체·소요시간·수동 개입·데이터/모델/프롬프트 버전을 기록한다.
- 실행 상태와 최소 운영 지표는 확인 가능해야 한다. 별도의 대규모 모니터링 제품 도입은 필수가 아니다.


### 9.3 운영 구현 기준

이번 개정은 v0.9.1.1 전체 요구를 승계하고 대시보드·로그의 구현 기준을 보완한다. 아래 신규 세부 설계는 **개정 권고안(팀 확인·구현 전)**이다. 기존 채택값은 유지하며, 완료 증거를 새로 주장하지 않는다.

운영 수치는 8.4의 채택값을 따른다. 과거 제안과의 비교는 부록 B에 기록한다.

**기술 선택 권고:** Auto Healing은 기존 LangGraph 흐름의 명시적 오류 분기와 코드 기반 Recovery Controller로 수행한다. 실제 LLM 호출·남은 시간·재시도 횟수를 공통 실행 상태에서 통제하고, 복구 조치는 허용 목록으로 제한한다. DB 컨테이너 재시작은 Docker에 맡긴다. LLM이 임의 명령이나 Docker 소켓을 사용하는 구조로 확대하지 않는다.

로그는 Python 표준 logging의 JSON formatter로 구조화하고, **PostgreSQL 조회용 이력 + DB와 독립된 영속 JSONL**을 사용하도록 권고한다. FastAPI가 운영 조회 API를 제공하고 기존 React·TypeScript의 /admin 화면이 조회한다. 현 프로젝트 규모에서는 별도 로그 서버를 필수 구성으로 추가할 필요가 없다. 향후 로그량·검색 요구가 커지면 전용 수집·검색 체계를 별도 검토한다.

### 9.4 운영 대시보드 네 영역

| 영역 | 권고안 채택 시 필수 표시 | 운영자가 판단할 내용 |
|---|---|---|
| 전체 상태 | API 생존, DB 준비, worker 최근 heartbeat, 수집 마지막 결과 및 확인 시각; 당일 접수·대기·진행·성공·기능 축소·실패·안전 중단 수 | 서비스가 응답 가능한지, 작업이 정체됐는지 |
| 실행 이력 | run_id, 시작/완료 시각, 단계·에이전트, 단계별 소요시간, 실제 LLM 호출 수, 최종 실행 상태, 추천 결과 유형·후보 수, 오류 요약 | 특정 요청이 어디서 지연·실패했는지 |
| 장애·복구 이력 | incident_id, 오류 유형, 감지 시각, 영향 단계, 시도 횟수, 복구 조치, 검증 결과, 자동/대체/수동/미복구, 알림 전송 상태 | 어떤 조치로 복구됐으며 사람의 개입이 있었는지 |
| 데이터 상태 | 마지막 수집 시도·성공 시각, 데이터 나이·24시간 만료 여부, 수집 전체·검수 완료·당일 적격 수, 제외 사유별 수, 사용 스냅샷 ID | 후보가 적은 이유가 정상 조건인지 데이터 장애인지 |

추천 후보 0건은 정상 NO_MATCH일 수 있으므로 오류로 집계하지 않는다. 데이터 상태의 당일 적격 수는 선택 배편과 구간에 따라 달라지므로 조회 조건을 함께 표시한다. CPU·메모리·토큰 차트는 선택 사항이다.

상태 집계는 접수 시각이 선택 기간에 속하는 고유 run_id를 대상으로 한다. 접수 수는 대기·진행 및 최종 상태별 수의 합과 일치해야 하며 마지막 집계 시각을 표시한다. worker heartbeat 지연 기준은 설정으로 명시하고, 관측 실패를 정상 상태로 표시하지 않는다.

**요청 예산 계약 권고:** accepted_at은 필수 작업 저장에 성공한 접수 시각, execution_started_at은 worker 시작 시각이다. deadline_at=accepted_at+90초로 정해 대기·재시도·재시작 후 재개에도 유지한다. 만료된 대기 작업은 실행하지 않고 안전 중단으로 기록한다. 90초 수치는 변경하지 않으며, 이 시작점 상세는 팀 확인 전 권고안이다.

기본 조회는 KST 당일, 자동 갱신은 10초와 수동 새로고침을 권고한다. 기간·상태·오류 유형·실제 운영/시험 필터, 실행 상세→단계→장애 상세 연결을 제공한다. 기본은 **조회 전용**이며 수동 수집 버튼은 후속 선택 사항이다.

### 9.5 로그 저장·전달과 장애 중 조회

- 공통 event_id를 가진 구조화 이벤트를 API와 worker에서 생성한다. 프로세스별 JSONL 파일을 영속 마운트에 기록하고 PostgreSQL 이력으로 적재한다. 다중 프로세스가 하나의 회전 파일을 경쟁적으로 쓰지 않도록 파일을 분리한다.
- DB 장애 시에도 JSONL에 기록한다. 재연결 뒤 event_id의 유일성 제약으로 중복을 제거하며 재적재한다. 재적재 위치를 기록하고, 완료 전인 로그를 이미 DB에 저장한 것으로 표시하지 않는다. 원본 이벤트와 요약 상태 갱신을 분리하고, 실행·장애별 상태 버전으로 오래된 이벤트가 최신·종료 상태를 덮어쓰지 못하게 한다. 재적재 커서는 DB 트랜잭션 커밋 후에만 전진시킨다.
- JSONL도 기록하지 못하면 stderr와 운영 알림에 기록 실패를 남긴다. DB 독립 저장은 EC2 자체 장애까지 견디는 고가용성 저장을 뜻하지 않는다.
- 운영 API는 PostgreSQL을 주 조회원으로 사용한다. DB 중단 시 이력 화면에는 **이력 조회 불가**, 마지막 성공 조회 시각을 표시한다. 0건·정상으로 대체하지 않는다. JSONL을 브라우저에 직접 공개하지 않고 운영자가 서버에서 확인한다.
- DB 로그와 JSONL은 7일 보존을 적용한다. 순환 정책·용량 한도를 설정하고 미전송 기록 손실 시 누락을 표시한다. FT 원자료는 만료 전 제출 증빙으로 별도 보존한다.
- 원문 프롬프트·응답 전문은 기본 저장하지 않는다. 오류 메시지·URL을 정제하고 비밀값·세션 토큰·개인정보는 제거한다. 근거 ID·버전·검증 결과 중심으로 저장한다.

### 9.6 공통 로그 필드와 논리 저장 구조

| 분류 | 필드 | 규칙 |
|---|---|---|
| 식별 | event_id, request_id, run_id, step_id, handoff_id, incident_id, state_version | 해당하지 않는 값은 null. event_id는 재적재 중복 제거 키 |
| 시간·출처 | occurred_at, ingested_at, duration_ms, service, worker_id, environment, is_test, deployment_sha | 시각은 UTC 저장·KST 표시. 시험/운영 분리 |
| 실행 | agent_role, event_type, execution_status, result_type, candidate_count | 실행 성공과 후보 없음 구분 |
| 오류 | error_code, error_category, severity, retryable, sanitized_message | 오류 분류는 코드에서 통일 |
| 복구 | attempt_no, retry_count, action, incident_status, service_mode, recovery_status, recovery_started_at, recovered_at, manual_actor | 최초 시도는 attempt_no=1, 추가 재시도는 retry_count=0부터 |
| 검증 | verification_steps, verification_passed, failure_reason | DB 준비·조회·필수 저장·API 검증 결과를 개별 기록 |
| 예산·근거 | llm_call_count, remaining_ms, model_version, prompt_version, snapshot_id, evidence_refs | SDK 내부 재시도 포함 실제 호출 기록 |
| 알림 | notification_status, channel_ref, sent_at, notification_error | 알림 성공을 복구 성공으로 계산하지 않음 |

논리 저장 단위는 **runs(요청 요약), run_events(단계 이벤트), incidents(장애 및 복구), collection_runs(수집 결과)**로 권고한다. 기존 스키마가 있으면 동일 의미를 매핑하고 중복 테이블을 만들지 않는다. 시간·상태·run_id·incident_id 조회에 필요한 인덱스를 두고, 상세 이력은 페이지 단위로 반환한다.

### 9.7 복구 판정·지표·알림 계약

실행 상태와 장애 복구 상태는 별도 필드다. 장애의 개방/종료 여부는 incident_status(open/closed), 기능 제공 상태는 service_mode(normal/degraded/unavailable)로 별도 기록한다. 장애 상태는 진행 중 recovering, 자동 정상 복구 recovered_auto, 대체 제공 degraded_fallback, 수동 복구 recovered_manual, 미복구 unrecovered로 구분한다. 대체 제공 중 원래 의존성 장애가 계속되면 incident는 열린 상태를 유지한다. 후속 정상 복구 시 상태 변경 이벤트를 보존한다.

- 운영 자동 복구율 = 집계 구간에 감지된 고유 장애 중 자동 정상 복구 건수 / 같은 구간에 감지된 전체 고유 장애 수. 집계 시각과 진행 중 건수를 함께 표시한다. 열린 미복구 장애를 분모에서 빼서 성공률을 높이지 않는다. 시험용 자동 복구율은 10.3의 전체 주입 에피소드 기준으로 별도 산출한다. 재시도 이벤트는 장애 수에 중복 합산하지 않는다.
- 현재 복구 상태별 분포는 고유 incident의 최신 상태 한 개로 상호 배타 집계한다. 대체 제공 경험 건수/비율은 이력 지표로 별도 표시하며 현재 상태 분포와 합산하지 않는다. 후보 없음은 장애 분모에서 제외한다.
- 운영 복구시간은 장애 감지부터 서비스 검증 완료까지이며, 미복구에 0초를 넣지 않는다. 시험 복구시간은 10.3에 따라 장애 주입부터 측정하고 두 값을 섞어 평균내지 않는다. 자동/수동 복구시간을 분리한다.
- DB 복구는 D-13의 준비·조회·필수 저장·핵심 API 응답 검증이 모두 통과해야 한다. 진행 중 요청은 원래 90초 한도 안에서 종료하며, 시스템의 후속 복구가 이미 실패한 요청을 성공으로 바꾸지 않는다. 후속 회복 관측은 요청과 분리한 worker 주기 작업을 권고하며, Docker 제어 권한 없이 서비스 검증 후 incident를 닫는다. 관측 루프의 시작·주기 실행은 장애 중인 DB 작업 큐에 의존하지 않아야 하며 DB 오류로 종료되지 않게 한다. 기존 worker 내 독립 타이머 등으로 구성하고 결과는 독립 로그에 남긴 뒤 재연결 시 반영한다. 새 서비스 도입은 필수가 아니다. 주기·관측 기한·실행 소유자는 첫 장애 시험 전 확정한다.
- 자동 재시도로 정상 회복한 일시 오류는 로그를 기본으로 한다. 재시도 소진·기능 축소·장애로 인한 안전 중단·수집 실패·CI 실패는 Discord 알림 대상이다. 정상 조건 탈락·후보 0건은 제외한다.
- incident_id + 상태 전환으로 중복 알림을 제한하고, 같은 의존성 장애로 다수 요청이 실패하면 운영 장애 한 건에 연결한다. 알림 실패도 저장하며 알림 경로의 재시도가 추천 작업을 무한 연장하지 않는다.
- 기존 알림 담당 박서윤, 부재 시 임익현을 유지한다. DB 반복 재시작 경고 임계값·DB 재연결 횟수와 간격은 기존 미정 항목으로 유지하고 첫 장애 시험 전에 확정한다.

### 9.8 운영 API·접근·수용 기준

기존 실행·장애 API에 GET /api/admin/overview, GET /api/admin/runs/{run_id}, GET /api/admin/collections를 보완하는 계약을 권고한다. GET /api/admin/runs와 GET /api/admin/incidents를 유지한다. 모든 운영 API는 서버에서 관리자 권한을 검사하며 화면 경로를 숨기는 것으로 인증을 대체하지 않는다. 관리자 인증 수단은 구현 담당자가 확정한다.

- [ ] 정상 요청 한 건의 run_id로 단계·LLM 호출·후보·최종 결과를 추적할 수 있다.
- [ ] 같은 장애의 재시도는 장애 수를 늘리지 않는다. 동일 알림 대상 상태 전환을 재처리·재적재해도 중복 발송하지 않으며 새 유효 상태 전환 알림은 별도 허용한다.
- [ ] DB 중단 중 JSONL 기록과 화면의 조회 불가 표시가 유지되며, 복구 후 중복 없이 이력이 재적재된다.
- [ ] 자동 정상 복구·기능 축소·수동 복구·미복구·진행 중을 구분하고 시험 데이터는 운영 통계에서 기본 제외한다.
- [ ] 스냅샷 만료·정상 후보 0건·수집 실패를 화면에서 구별할 수 있다.
- [ ] 권한 없는 운영 API 요청이 차단되고 비밀값이 로그·응답에 노출되지 않는다.

위 항목은 권고안 채택 시 적용할 수용 기준이며 이 문서 개정으로 채택 또는 통과한 것은 아니다. 12.1 아키텍처 개정 시 복구 상태, 로그 스키마, DB 장애 중 기록·재적재, 운영 조회 권한을 함께 구체화한다.

### 10.2 공통 필수 장애 시험

| ID | 주입·감지 | 기대 대응·증빙 |
|---|---|---|
| FT-01 | 외부 LLM API 지연 mock 등으로 client timeout 재현 | 제한 재시도, 같은 검증 후보의 기본 정보 대체/중단, 실제 호출·시각·결과 기록 |
| FT-02 | 에이전트 단계 강제 예외, 일회성·지속성 구분 | 안전한 단계 재실행, 한도 종료·알림, 중복 저장 차단 |
| FT-03 | 격리된 PostgreSQL **비정상 프로세스 종료**와 **수동 stop/연결 차단**을 주입법별 구분 | 비정상 종료: Docker 자동 재시작 + 앱 재연결·조회·필수 저장·API 응답 검증. 수동 `stop db`/차단: A안 재접속·이용 불가·Discord·독립 로그, 필요한 경우 수동 복원 후 검증. 두 유형을 동일한 자동 복구 성공으로 집계하지 않음 |
| FT-04 | 비JSON·필수키 누락·잘못된 타입의 LLM mock | 검증 차단·수정 요청 한도·기본 정보/중단, 무효 출력 미노출 |

각 FT는 3회 이상 독립 반복한다. 최초 시도와 내부 재시도를 독립 시험 횟수로 세지 않는다. 필수 네 유형에 더해 문화행사 수집 실패·오래된 성공본·업무 재탐색 한도는 제품 회귀 사례로 검증한다.

FT-03은 연결·조회·필수 저장 실패 시험이며 데이터 삭제·훼손·백업 복원 시험이 아니다. **격리된 시험 대상**과 복원 절차를 먼저 정한다. 기존 필수인 FT-03 독립 반복 3회 이상을 충족하고, 가능하면 비정상 종료 자동 복구 시험과 수동 중지/연결 차단 시험을 **각 유형별 3회씩** 수행한다(유형별 3회는 추가 권장, 공식 최소와 구분). 매 회 주입방법·자동 재시작 발생 여부·DB 준비·조회·쓰기·API 재연결·알림·복구시간·수동 개입을 기록한다. 실패/미복구를 분모에서 제외하지 않는다. Docker 정책은 수동 `docker compose stop db`를 되돌리지 못하므로 강사에게 이 명령으로 자동 복구까지 평가하는지 확인한다.

### 10.3 판정과 지표

- 장애 에피소드: 장애 주입이 확인된 독립 시험 1회. 같은 실행의 재시도는 같은 에피소드이며 감지 실패도 분모에 포함한다.
- 시험 PASS: 사전에 정의한 기대 대응을 충족했는지. DB 중단 안내·알림이 정상 동작해도 복구 성공과 같지 않다.
- 자동 복구율: 수동 개입 없이 원래 요구한 정상 서비스가 회복된 에피소드 수 ÷ 전체 장애 에피소드 수 × 100.
- 기능 축소 대체율: 기본 정보·허용된 과거 성공본으로 제한된 응답을 제공한 비율을 별도 제시한다. 설명·검토 중단을 정상 기능 복구로 합산하지 않는다.
- 시험 복구시간: 장애 주입 시각부터 필수 복구 검증을 모두 통과한 정상 서비스 응답 시각까지. DB는 D-13의 준비·조회·필수 저장·핵심 API 응답을 모두 확인한다. 미복구는 N/A이며 0초로 처리하지 않는다.
- 평균 복구시간: 자동 정상 복구 성공 건의 시간 합 ÷ 성공 건수. 유형별 반복 횟수·성공/실패·원인도 제시한다.

업무상 후보 없음·조건부 내부 제외는 장애 발생을 의미하지 않으며 장애 주입 분모에 넣지 않는다. 복구 가능한 시험만 선택해 분모를 줄이지 않는다. 자동 정상 복구·기능 축소 대체·수동 복구·미복구를 구분하고 각 회차의 원자료를 보관한다. 가이드의 예시 재시도 횟수·시간을 팀의 실측값으로 옮겨 적지 않는다.

### 10.4 배포·CI/CD

기존 결정인 React·TypeScript, FastAPI, PostgreSQL Docker, EC2, GitHub Actions→ECR→SSH→Compose, Discord를 승계한다. 구체적 컨테이너 분리·worker·스케줄러·ORM·드라이버는 아키텍처/배포 명세에서 정한다.

필수 완료 조건:

1. Compose로 프론트·백엔드·DB와 채택한 실행 구성 전체를 연결한다. DB 영속 볼륨, 서비스명 기반 통신, secret, health/readiness, 필요한 파일·마이그레이션을 확인한다.
2. 커밋 시 정적/스키마 검사·단위·통합·필수 장애 기대 대응을 자동 검증한다. CI에서는 고정 응답/mock을 기본으로 하고 실제 API·LLM 연결은 별도 smoke 결과를 남긴다.
3. 의도적 assertion 실패로 테스트 실패→배포 미실행→배포 버전 불변→Discord 실패 알림·담당자 멘션을 1회 이상 증빙한다. 기대한 장애 대응을 통과한 FT를 무조건 실패한 테스트로 취급하지 않는다.
4. 검사한 커밋과 빌드·배포 이미지의 SHA/digest를 연결한다. 배포 후 핵심 흐름 확인이 실패하면 배포 성공으로 기록하지 않는다.
5. EC2 외부 접속과 실제 PostgreSQL·LLM 연결, 시간표·검수 파일 접근, 핵심 추천 흐름을 제출 버전에서 확인한다.

자동 배포·롤백은 필수 이후 확장이다. 수동 배포 단계를 쓰더라도 실패한 검사의 SHA는 승인된 배포 경로에서 차단되어야 한다. 롤백을 채택하면 이전 정상 이미지 복귀 후 readiness·핵심 흐름을 다시 확인하며 DB 데이터·스키마 자동 되돌리기와 구분한다.

코드 커버리지 **70% 이상과 핵심 테스트 전부 통과**를 회의 게이트로 채택한다. 커버리지는 숫자만으로 완료를 판단하지 않는다. 핵심 시간 계산·입출력 검증·상태 전이·복구 정책의 분기 및 필수 사례 통과를 함께 요구한다. Backend 담당자가 첫 CI 통합 전에 측정 대상과 제외 범위를 명시하고 실제 실행 결과를 보관한다. 수치 선택만으로 기준을 충족했다고 표시하지 않는다. 브랜치는 `dev` 개발→PR 검토→`main` 배포 경로를 채택하며 필수 실패가 있으면 `main` 배포를 차단한다.

다음 표는 팀원 수정본의 구현 세부안을 기존 결정과 통합한 것이다. 정확한 패키지 버전·호환성·현재 서버 상태는 이번 문서 작업에서 검증하지 않았다. ‘제안’은 첫 통합 전에 담당자가 설치·연결 시험 후 채택 또는 대체 근거를 기록한다.

### 12.1 멀티 에이전트 아키텍처 설계서에 전달할 변경

### 13.2 데이터·API 세부 계약 승계

- 기존 이동 응답의 의미는 유지한다: from_stop_id, to_stop_id, departure_time, travel_minutes, estimated_arrival_time, arrival_time_source. arrival_time_source는 calculated다. 날짜·시간대·일자 차이·근거 버전을 추가하여 자정 경계를 보존한다. 기존 HH:mm 값만으로 날짜를 잃지 않는다.
- v0.6 행사 출력의 event_id, reason, evidence_refs, uncertainties, visitability와 공개 표시 title, category, place, distance_km, distance_type, date, time, fee, official_url, last_collected_at의 의미를 보존한다. preference_match는 D-11에 따라 폐기한다. uncertainties에 필수 방문 정보 누락이 있으면 해당 후보를 공개하지 않는다. 요금 등 비필수 정보 누락은 구분해 표시한다. 실제 필드명·중첩 구조는 하위 API 계약으로 정한다.
- 원문 소요시간에는 임의 정차·대기·실시간 지연을 추가하지 않는다. 행사장까지의 검수한 하선·이동·대기는 별도 일정 항목이다. 과거 역방향 소요시간 추정은 현재 해당 날짜의 운항 확인과 구분한다.
- 배편 운임 안내 방향은 승계한다. 공식 출처·적용일·요금 조건을 확보해야 하며 미확보 시 확인 필요로 표시한다. 행사 무료와 배편 무료를 혼동하지 않는다. 여행 전체 금액 예산 최적화·충족 판정은 이번 범위에서 제외한다.
- 자유문 취향 입력·무료 여부 필터·개인화 점수는 D-11로 제외한다. 범용 자유대화 챗봇·즐겨찾기·개인화 이력·필수 혼잡도·전통시장/고정 장소 연계도 필수 범위에 넣지 않는다.
- MVC 관심사 분리 원칙을 유지한다. Controller는 요청·권한, Model 계층은 업무·계산·저장소, View는 공개 JSON, schemas는 입출력 계약을 맡는다. 구체적 파일 구성은 아키텍처 문서의 MVC·모듈 구조를 따른다.
- 운영 진입점은 실행 목록과 장애 목록을 제공하고 서버 권한을 검사한다. 기존 초안 경로는 GET /api/admin/runs, GET /api/admin/incidents다. GET /health/live는 생존, GET /health/ready는 DB·필수 설정·데이터 준비를 구분한다. LLM 일시 오류를 프로세스 사망으로 간주하지 않는다. 기존 GET /health와의 호환은 실제 코드 확인 후 정한다.

### 13.3 운영·배포 세부 승계

- LLM 공급자는 기존 OpenAI API 선택을 승계한다. 프레임워크는 LangGraph StateGraph 채택 방향을 따르며, 모델·프롬프트·세부 호출 방식은 미정이다. 공급자 변경은 명시적으로 기록한다.
- Frontend·Backend CI는 각각 검사·알림을 유지하고 실패한 영역의 담당자를 멘션한다. 전체 필수 검사의 결과를 배포 게이트로 결합하며 필수 실패를 continue-on-error로 성공 처리하지 않는다. 정상 성공 실행과 의도적 실패 실행을 모두 증빙한다.
- 정적·스키마·비밀값 검사와 단위·통합·FT 검사를 연결한다. 실제 검사 도구·범위·커버리지는 담당자가 정하고 설정·실행 결과를 보관한다.
- 알림에는 커밋/이미지/파이프라인 또는 요청/장애 ID, 발생 시각, 실패 단계, 재접속 결과, 증빙 참조를 포함한다. 전송 실패·중복 제한을 검증한다.
- DB 독립 로그는 컨테이너 교체 후에도 필요한 증빙이 남도록 수집·마운트·보관 위치를 정한다. D-13의 자동 재시작 시각·시도 상태·서비스 복구 확인 결과와 자동/수동 개입을 로그로 분리한다. **로그 및 실행 기록 7일**을 설정값으로 채택하며, 로그 만료 전 FT 증빙은 보고서에 연결해 보존한다. 성공 수집 스냅샷은 최근 **2개**를 보관하되 24시간을 초과한 과거 스냅샷은 서비스 추천에 재사용하지 않는다. 수동 조치 담당자·조치 내용·시각·복원 후 검증을 장애 ID에 연결한다.
- 운영 조회는 실행·단계·처리시간, 오류·시도·대체/복구·검증 거부 사유, 수동 조치·배포 SHA·이미지·증빙을 제공한다.
- 정기 문화행사 수집은 매일 09:00 Asia/Seoul에 단일 작업으로 실행한다. 성공한 전체 배치만 승격하고, API 일부 실패 시 재시도 2회 이내로 종료한다. **전일 09:00 수집본이 24시간을 넘긴 경우** 새 수집이 실패했다는 이유로 오래된 결과를 정상 추천으로 노출하지 않는다. 시간표 JSON은 배포 이미지 포함 또는 읽기 전용 마운트로 접근 가능해야 한다. 기존 Dockerfile이 app만 복사했다는 과거 기록이 있으므로 실제 제출 이미지에서 데이터 접근을 검증한다.
- ECR 리전·태그·AWS 인증·SSH·Compose 명령·DB 권한/마이그레이션·로그 보관은 배포 명세에서 확정한다. 롤백 채택 시 이전 이미지 보관과 DB 스키마 호환성을 확인한다.
- P3-2 보고서에는 **자동 재시작 조건·한계·실패 시 수동 복구 runbook**을 함께 넣고, P3-3에는 게이트와 알림·선택 배포/롤백의 실제 결과를 포함한다. 세 보고서는 동일 제출 SHA·실행 ID·증빙 인덱스를 참조한다.

| 이 PRD | 누구의 어떤 문제를 해결하는지, 무엇을 제공하는지, 완료·실패 기준 | 사용자 결정과 근거를 기록해 버전 관리한다. |
| 멀티 에이전트 아키텍처 설계서 | 협업 구조 선택 근거, 역할·책임·입출력, Handoff·상태·종료·장애 격리 | PRD 요구사항 ID에 연결한다. 제품 범위를 임의로 바꾸지 않는다. |
| API·DB·화면·폴더 구조·구현 계획 | 구체적 계약, 저장 구조, 파일·모듈, 실행·배포 방법 | PRD와 아키텍처를 함께 만족시킨다. |
| 코드·시험·운영 보고서 | 실제 실행 및 측정 결과 | 설계 예정과 구현 완료를 구분하고 증빙을 붙인다. |

v0.9는 사용자 최종 결정이 반영된 로컬 v0.8을 기준으로 팀원 v0.8 수정본의 유효한 구현·운영 제안을 통합한다. 기존 v0.7 통합본을 승계하여 v0.6의 개정 본문과 그 뒤에 보존된 v0.5의 유효 요구사항 및 후속 결정을 포괄한다. 과거 문서는 이력이며 현재의 별도 명령 집합이 아니다. 과거의 공식 코스 중심 요구와 이번 문화행사 중심 요구를 동시에 구현하지 않는다. 현재 기준 문서는 docs/PRD.md와 아키텍처.md 두 개다. MVC·API·DB·실행 구조는 아키텍처 문서 안에서 관리하며, 충돌할 경우 PRD를 우선한다.

`확정`은 제품 결정, `승계`는 이전 문서에서 이어받은 결정, `제안`은 구현 초기안, `미확인`은 조사·시험이 필요한 상태를 뜻한다. 문서에 이름이 있다는 이유만으로 파일·데이터·기능이 구현됐다고 판단하지 않는다.

### A.3 추가 확정 사항: 현재 구현 기준

| ID | 사용자 결정 | 적용 규칙 |
|---|---|---|
| D-06 | 검수 가능한 행사 2~3개 확보 구간 | 당일 운영·운항·이동조건을 확인할 수 있는 출발→도착 1개 구간을 조사 후 선정한다. 예시 구간 자동 확정 금지. |
| D-07 | 실제 추천 대상 약 3개 | 초기 운영 검수 목록은 최대 3개 행사로 제한한다. 그 안에서 당일 배편 조건을 통과한 실제 수만 노출한다. 0~2개도 허용하며 추가 후보를 만들지 않는다. |
| D-08 | 전시 중심 | 최초 검수·시연은 전시를 우선한다. 공연 확대는 필수 아님. 정시 회차형 자료가 들어오면 전시 산식으로 잘못 승인하지 않는다. |
| D-09 | 하선 후 30분 이내 이동 | 하선 지점부터 행사장 입구까지 검수한 예상 이동시간이 30분 이하일 때만 추천한다. 30분 포함, 초과·미상 제외. 이동수단 자체는 이번 결정에서 한정하지 않았으며 실제 수단·경로와 필요한 대기/환승시간을 검수해야 한다. |
| D-10 | 조건부 후보 지양 | 조건부 후보를 별도 카드로도 제시하지 않는다. 필수 조건이 확인된 POSSIBLE 후보만 추천하고 제외 사유는 내부 trace에 보관한다. |
| D-11 | 취향·무료 여부 입력 제거 | 자유문 취향·선호·무료 필터·개인화 점수를 제거한다. LLM은 이동/일정 검토, 근거 기반 추천 이유 작성, Critic 검토에 사용한다. 요금은 원천 정보로만 보존·안내한다. |
| D-12 | 당일 조회에 집중 | 사용자 조회일은 Asia/Seoul의 오늘로 설정한다. 당일 운영 중인 검수 전시와 아직 출발하지 않은 배편을 대상으로 시연한다. 과거 고정 날짜 자료를 당일 행사처럼 사용하지 않는다. |
| D-13 | 실서비스 운영 중 DB 컨테이너 비정상 종료 자동 재시작 | PostgreSQL은 Compose에서 `restart: unless-stopped`를 적용한다. 비정상 프로세스 종료 뒤 Docker가 컨테이너를 다시 실행하도록 설정하고, DB 준비·조회·필수 저장·FastAPI 정상 응답까지 확인해야 복구로 판정한다. 의도적인 수동 중지·DB 무응답은 이 설정만으로 자동 복구되지 않음을 명시한다. |

배 출발부터 총시간 예산과 하선 후 이동 30분은 별개의 제약으로 함께 적용한다. 총시간을 입력하지 않으면 임의의 90분을 부여하지 않는다. ‘조건부 후보는 별로’는 추천에서 제외하는 의미로 반영했다. 당일 조회는 방문일 기준이며 API 실시간 갱신을 뜻하지 않는다. 하루 1회 수집·수집시각 표시·현장 변경 비보장 원칙을 유지한다.

### A.7 v0.9.1.1 사용자 확정: DB 장애 시 자동 복구 범위

- **확정(운영 정책):** 실제 서비스에서 PostgreSQL 컨테이너의 **예상하지 못한 프로세스 종료**가 발생하면 Docker가 다시 띄우도록 `compose.yaml`의 `db` 서비스에 `restart: unless-stopped`를 적용한다. DB 데이터는 영속 Volume을 사용하고 컨테이너 재생성·재시작 때문에 삭제하지 않는다.
- **복구 판정:** Docker가 DB 컨테이너를 다시 시작한 것만으로 성공 처리하지 않는다. PostgreSQL 준비 확인(`pg_isready` 등) → FastAPI의 DB 재연결 → 실제 `SELECT` 조회 → 테스트용 안전한 필수 저장/트랜잭션 → 서비스 핵심 API 응답이 정상이어야 **자동 정상 복구**다. 실패하면 이용 불가·Discord·독립 로그와 운영자 대응 절차를 유지한다.
- **설정의 한계:** 운영자가 `docker compose stop db`로 **의도적으로 정지**하면 `unless-stopped`만으로 자동 재시작되지 않는다. 컨테이너가 실행 중인 채 DB 응답만 멈춘 경우에도 `healthcheck` 단독으로 자동 재시작하지 않는다. 디스크 손상, 잘못된 설정, EC2 자체 장애도 해결되지 않는다.
- **FT-03 검증:** (A) PostgreSQL 프로세스/컨테이너의 **비정상 종료**와 (B) 수동 `stop db` 또는 연결 차단을 **서로 다른 주입 사례로 분리**한다. A에서 Docker 자동 기동과 서비스 회복을 검증하며, B에서 기존 A안의 재접속·안내·알림·독립 로그를 검증하고 통상 수동 복원이 필요함을 기록한다. B에도 무인 자동 재가동이 필수인지 **강사 확인** 전에는 완료로 표기하지 않는다.
- **미채택:** LLM 에이전트에 Docker 소켓/관리자 권한을 주어 컨테이너를 조작하거나, 외부 감시 프로그램을 도입해 의도적인 관리자 중지까지 무조건 되돌리는 방식은 채택하지 않는다. 해당 범위가 평가 필수로 확인되면 별도 결정한다.
- **주의:** `unless-stopped`는 `on-failure:3` 같은 정해진 재시작 횟수 제한을 제공하지 않는다. 연속 실패 시 반복 재시작 기록을 남기고 Discord 경고 및 운영자가 원인을 확인할 수 있게 한다. 경고 기준·DB 접속 재시도 횟수/간격은 첫 장애 시험 전 구체 설정이 필요하다.
